## Lead clarification — identity and historical receipt compatibility

Diagnostic basis: `codex/portfolio-review-20260922@b727cfcf2d7bc497e531a4223788a11b51c3a20b`, `CODEX_R29A_DIAGNOSTIC_20260922.md`.

The proposed compatibility direction is approved with the following exact representation.

### 1. Manifest identities

The R29a packet's new identities are authoritative for the new manifest generation:
- `local.sandbox@1`
- `mcp.echo@1`
- `browser.session@1`

Do **not** add aliases for accepted-base `local.sandbox@1.0`, `api.mcp.echo@1.0`, or `browser.session@1.0`. Do not rewrite/upgrade historical approvals. Bounded current callers/tests must move explicitly to the new identities, and an old approval/version pin must fail rather than silently migrate.

Adding `config/integrations/browser.session@1.json` is required because the native R29a surface already requires `BrowserSessionAdapter` to stop constructing an inline manifest.

### 2. Dynamic legacy adapter

`LegacyToolCallAdapter` may keep a generated manifest because its operation catalogue comes from the injected legacy capability registry and it is not a built-in adapter under `tools/adapters/`.

That generated manifest must:
- validate through the same new `AdapterManifest` schema;
- use the new vocabulary only;
- preserve each operation's declared scopes, including literal `network` authority for network tools;
- have a canonical `manifest_digest()` computed exactly like file-backed manifests;
- bind that real digest into every new V1.7 receipt produced through the legacy bridge.

Do not invent a static legacy operation catalogue.

### 3. Historical receipt readback

`ActionReceiptV17.manifest_digest` remains a **required string for newly constructed receipts**. It must have **no model default** that could allow new gateway code to omit a real digest.

Approved historical marker:

`historical-unbound`

Use it only in the durable receipt **read-compatibility path** when an already-persisted JSONB receipt has no `manifest_digest` key. The repository may centralize this in a helper such as `_receipt_from_payload(payload)`:
- if the key exists, validate/preserve it;
- if the key is absent, copy the payload and inject exactly `manifest_digest="historical-unbound"` before model validation;
- never mutate/backfill the stored JSONB row;
- never compute today's/current manifest hash for a historical receipt.

All new gateway receipt builders must pass the real canonical 64-hex digest from the adapter manifest. Add a negative test proving a newly constructed `ActionReceiptV17` without `manifest_digest` fails validation, plus a compatibility test proving old JSONB readback returns `historical-unbound` without changing storage.

The historical marker is provenance state, not a digest and must never satisfy any future equality check that requires binding to a current manifest.

No SQL column migration is required for this slice because the receipt body is already JSONB.

### 4. Secret guard

Recursive scanning of **string keys and string values** is approved and conservative. Apply the packet's exact secret-like regex; do not broaden this into credential discovery, trust, signing or install lifecycle.

These clarifications do not release R28d or any live/provider/model action.
