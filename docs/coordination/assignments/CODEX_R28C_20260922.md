## Lead clarification — legacy fence plumbing

The proposed bounded plumbing is **approved for R28c**.

The frozen legacy `ToolCall` supplies `task_id`, `attempt_id`, and its claimed `lease_generation`, but has no `mission_id` or `cancellation_generation`. `ActorContext` supplies only authenticated actor/project. The accepted V1.7 gateway correctly requires all consequential fence fields and must continue comparing the envelope claims to `FenceProvider.current` plus the committed reader.

There is no existing trustworthy legacy field that can supply the missing mission/cancellation claims without changing the frozen protocol or silently upgrading caller authority.

Therefore R28c may add **optional trusted constructor bindings** on legacy `ToolGateway`:
- `mission_id: str | None = None`
- `cancellation_generation: int | None = None`

These are plumbing claims, not authority. For a side-effecting legacy call:
- missing mission/cancellation binding fails closed before delegation;
- do not infer mission from project/task, query a "current" cancellation value to fill the envelope, or invent defaults;
- keep `task_id`, `attempt_id`, and `lease_generation` from the frozen `ToolCall`;
- keep actor/project from authenticated `ActorContext`;
- the V1.7 `FenceProvider.current` and transaction reader remain authoritative and reject stale/mismatched claims.

`permission_mission.py` may explicitly create/bind a local durable mission/task-attempt lease and pass the resulting trusted mission id and cancellation-generation snapshot into the legacy gateway. It must use the V1.7 durable approval grant for the delegated consequential effect; the frozen legacy `Approval` object is not authority for the V1.7 boundary.

Do not modify `contracts/protocols.py` or `ToolCall` for this bridge. Do not add an authority resolver in R28c; if a general runtime needs one later, it must be a separately reviewed seam rather than a hidden fallback.
