## Why

`reserve` is SELECT-then-INSERT and `mark_executing` is read-modify-write (`src/swarm/tools/effects.py:225-270`). Two processes can both execute the same consequential effect, and a different payload can ride an existing `effect_key` and inherit its receipt.

- new `tests/integration/db/test_effect_reservation_atomic.py`

## Exact behavior

1. `DurableEffectRepository.reserve(envelope) -> dict`:
   1. `sqlalchemy.dialects.postgresql.insert(ActionEffectRow).values(...).on_conflict_do_nothing(constraint="uq_action_effect_project_key")`.
   2. Select the row by `(project_id, effect_key)`.
   3. Compare the stored `integration_id`, `integration_version`, `operation`, `destination_digest`, `payload_hash` with the envelope-derived values. Any difference → `EffectConflictError("effect_key_binding_mismatch")`.
   4. Return the row dict plus `"created": bool` (true only for the inserting caller).
2. `mark_executing(*, project_id, effect_key, executor_id) -> dict` is a single statement:
   `UPDATE action_effects SET state='executing', started_at=now(), executor_id=:e, attempt_count=attempt_count+1 WHERE project_id=:p AND effect_key=:k AND (state='reserved' OR (state='failed' AND state_reason='not_applied')) RETURNING *`.
   Zero rows → re-read and raise exactly one of: `effect_not_found`, `effect_already_succeeded`, `effect_unknown_requires_reconcile`, `effect_already_executing`, `effect_terminal:<state>`.
3. `InMemoryEffectStore` mirrors both rules (same error strings, `attempt_count`, `executor_id`, `created`).
4. The gateway passes `executor_id=new_id("exe_")`; no other gateway change.

`failed` is re-executable **only** with `state_reason == 'not_applied'`. Until R28a lands nothing sets that reason, so after this packet every `failed` effect is terminal. That is intended: it closes E6 immediately.

## Negative tests (marker `integration`; real threads, independent sessions, `threading.Barrier`)

Each thread builds its own `Session` and repository and calls `session.commit()` after every repository call (transaction ownership moves into the repository in R27c). Under PostgreSQL READ COMMITTED the losing `INSERT … ON CONFLICT` waits for the winner's commit and then inserts nothing; the losing `UPDATE` waits on the row lock, re-evaluates its `WHERE`, and matches zero rows. The tests prove exactly that.

- `test_concurrent_reserve_same_key_one_row` — 8 threads: one row, identical `effect_id`, exactly one `created is True`, no `IntegrityError` escapes
- `test_concurrent_mark_executing_single_winner` — 8 threads: one success, seven `effect_already_executing`
- `test_reserve_binding_mismatch_payload`, `test_reserve_binding_mismatch_destination`, `test_reserve_binding_mismatch_operation` — same explicit `effect_key`, one differing field → `effect_key_binding_mismatch`
- `test_failed_without_not_applied_reason_is_terminal`
- `test_project_b_same_effect_key_is_independent`

## Evidence gate

Run the file five times in a row (`for i in 1..5`) against real Postgres; all green; save the five outputs. A flaky pass is a fail.

## Exit

Tests green five consecutive runs; ruff and mypy clean.

## Do not

Do not introduce advisory locks, a second table, or an in-process lock as the authority. Do not change transaction ownership (R27c).

## Forward-compat

V2.3 `DispatchIntent` treats an effect reservation as one resource component. The `created` flag and the single-winner CAS are what make its compensation idempotent; keep both.
