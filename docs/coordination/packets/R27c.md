## Why

The repository only flushes and the gateway never commits (`effects.py` throughout; `v17_gateway.py:127-161`). The reservation is invisible to other processes while the adapter runs, and a crash rolls it back, so a retry executes again. Approval use is recorded after success and non-atomically (`v17_gateway.py:247-248`), so a one-shot approval can authorize several concurrent effects.

ART-V20-INTEGRATION-CONTRACT already fixes the ownership rule: the gateway receives an injected `EffectRepository`; adapters never own DB transactions.

## Exact behavior

1. `DurableEffectRepository(session_factory: sessionmaker[Session])`. Every public method opens one short transaction with `swarm.db.engine.session_scope(factory)` and commits before returning. No method accepts or returns a live `Session`. Set class attribute `durable = True`; `InMemoryEffectStore.durable = False`.
2. New `begin_execution(envelope, *, executor_id, fence_reader: Callable[[Session], Mapping[str, int | None]] | None = None) -> dict` — **one transaction**, in this order:
   1. `SELECT … FOR UPDATE` the effect row; missing → `EffectStoreError("effect_not_found")`.
   2. If `fence_reader` is not `None`: `current = fence_reader(session)`, called **inside this transaction**. For every key in `current` whose value is not `None` (`lease_generation`, `cancellation_generation`), compare with the effect row's stored column of the same name; any difference → `EffectConflictError("fence_changed_before_execute")`. The reader is supplied by the lease module in R28b and takes `FOR SHARE` on the lease/attempt row, so a concurrent cancellation serializes against this transaction: no effect can start after a cancellation has committed. Until R28b the gateway passes `None`.
   3. If `envelope.approval_id` is set and the row's `approval_consumed_at IS NULL`: run
      `UPDATE approvals SET used_count = used_count + 1 WHERE id=:a AND project_id=:p AND revoked_at IS NULL AND expires_at > now() AND used_count < max_effect_count`.
      Zero rows → roll back and raise `EffectStoreError("approval_not_consumable")`. Otherwise set `approval_consumed_at = now()` on the effect row. A re-attempt of the same effect never consumes twice — but when `approval_consumed_at` is already set, still `SELECT` the approval and require `revoked_at IS NULL AND expires_at > now()`; otherwise roll back with the same `approval_not_consumable`. Revocation and expiry always stop a retry.
   4. Apply the R27b compare-and-swap to `executing`.
   5. Commit. Only after this method returns may the gateway call the adapter.
3. New `finalize_with_receipt(*, project_id, effect_key, state, state_reason, post_observation, external_id, reconciliation, receipt) -> ActionReceiptV17` — one transaction: CAS `WHERE state IN ('executing','unknown')` to the new state (zero rows → `EffectConflictError("finalize_state_conflict")`), set `finished_at`, `state_reason`, observations; insert the receipt (R27a rules); commit.
4. Gateway sequence becomes: validate → authorize → policy → fences → `get()` (succeeded → return `terminal_receipt`; unknown → reconcile) → `_require_exact_approval` → `reserve` → `begin_execution` → `observe_pre_state` → `execute` → `observe_post_state` → `finalize_with_receipt`. Remove the gateway's `record_approval_use` call. Map `approval_not_consumable` to `ApprovalInvalidError("approval_expired_or_revoked_or_exhausted")`.
   Note the order change: approval is validated **before** `reserve`, so a denied request leaves no durable row; the read-only `get()` keeps replay-of-succeeded working after the approval has expired.
5. `attach_pre_observation` stays a separate short transaction. `mark_executing` becomes the private helper `_cas_to_executing(session, …)` used only inside `begin_execution`; public `finalize` and `record_approval_use` are deleted from both stores. Update the R27b concurrency tests to drive `begin_execution` (same assertions).

## Do not

Do not hold a transaction open across `adapter.execute`. Do not add retries inside the repository. Do not refund approval use on failure: an attempt that reached the adapter may have had an effect.

## Forward-compat

`fence_reader` returns a mapping on purpose. V1.8 packet `18-04` adds the key `site_epoch` (plus one stored column) and step 2.2 compares it with no other change to the gateway or repository. The tools module never queries worker or site tables itself; the owning module supplies the reader.
