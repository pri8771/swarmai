## Why

CP5 (`V17_LIVE_CHECKPOINT_PROTOCOL.md`) requires three integrations on one shared boundary plus live negatives. The harness makes the run reproducible and the evidence uniform; the run itself is a separate packet so a failed run is preserved and never edited into a pass.

## Surfaces (R33a)

- new `scripts/r33_cp5_three_integrations.py`
- new `tests/scripts/test_r33_cp5_harness.py` (dry structure checks only)

R33b touches no source: evidence only.

## Exact behavior (R33a)

1. Preconditions, each a hard fail: `SWARM_DATABASE_URL` set and not the forbidden demo DSN; `alembic heads` equals the single expected head; working tree clean; `SWARM_ALLOW_PAID` unset or `false`.
2. Starts `python -m sandbox.live_fixture --port 0` as a subprocess with a random per-run `FIXTURE_PASSWORD`; tears it down in `finally`.
3. Builds one `AdapterRegistry` (`local.sandbox@1`, `http.notes@1`, `http.session@1`), one `DurableEffectRepository`, one gateway. All three integrations go through that single gateway object — assert `id(gateway)` is identical across steps and record it.
4. Positive steps: (a) `fs.write_text` + `proc.run` in a temp worktree; (b) `notes.list` + approved `notes.create`; (c) `page.open` + approved `form.submit`.
5. Live negative steps, by case ID from `R32a`: N17-01, -03, -04, -07, -08, -10, -11, -14, -15, -16, -17, -18, -23, -24. N17-14/-15 use real child processes; N17-14 includes a `os._exit(9)` child between `begin_execution` and finalize.
6. Output directory `docs/evidence/v17-checkpoints/CP5/<run-id>/` (`run-id = cp5-<UTC timestamp>`; refuse to write into an existing directory): `manifest.json` (source SHA, migration head, manifest digests, policy version, python/OS, Postgres version, `spend_usd: 0`), `commands.json`, `environment.json` (names of env vars used, never values), `receipts.jsonl`, `fixture-state.json` (before/after each step), `cases.json` (case id → expected, observed, pass), `summary.md`.
7. Exit code `0` only if every step and case passed. On any failure still write the full directory with `result: "fail"`.

## R33b procedure

Run the harness once on the exact pushed tip. Commit the directory untouched. If it fails: commit it, classify the failure in `summary.md`, open a fix packet, and run again into a **new** run-id. At most three runs before stopping for lead triage.

## Negative tests (R33a)

- `test_harness_refuses_dirty_tree`, `test_harness_refuses_existing_run_directory`, `test_harness_refuses_paid_mode`, `test_environment_json_has_no_values`

## Exit

R33a: tests green, harness runs end to end locally. R33b: one committed run directory with `result: "pass"` bound to the pushed tip SHA; status `live_checkpointed`; heartbeat notes `review_pending`.

## Do not

Do not mark CP5 accepted. Do not rerun into the same directory. Do not count a run made on a dirty or unpushed tree.
