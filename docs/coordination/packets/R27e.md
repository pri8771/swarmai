## Why

A process that dies between `begin_execution` and `finalize_with_receipt` leaves the row `executing` forever. The only safe reading of such a row is "outcome unknown". It must never return to `reserved`.

## Exact behavior

1. New repository method `recover_orphaned(*, project_id, effect_key, grace_seconds: int, timeout_seconds: int) -> bool` — one transaction:
   `UPDATE action_effects SET state='unknown', state_reason='executor_lost', finished_at=now() WHERE project_id=:p AND effect_key=:k AND state='executing' AND started_at < now() - make_interval(secs => :timeout + :grace)`. Returns `True` when a row changed.
2. Gateway: when `get()` shows `executing`, call `recover_orphaned(grace_seconds=30, timeout_seconds=envelope.timeout_seconds)`. `True` → continue on the `unknown` path. `False` → raise `EffectConflictError("effect_already_executing")` (a live executor may still be running).
3. Reconcile verdicts (adapter `reconcile` result key `state`): `succeeded` → effect `succeeded`; `not_applied` → effect `failed` with `state_reason='not_applied'`; anything else → stays `unknown`, raise `ReconciliationRequiredError("external_outcome_still_unknown")`. Every reconcile call writes a receipt (`reconciliation_state` = `reconciled` or `pending`).
4. Class gate after a `not_applied` verdict: side-effect class `consequential` → the same call may continue to a new attempt (`begin_execution` again; approval already consumed for this effect, R27c). Class `irreversible` → never re-execute automatically: raise `ReconciliationRequiredError("irreversible_requires_operator_disposition")`. New repository method `rearm_irreversible(*, project_id, effect_key, operator, reason)` sets `state_reason='not_applied'` with an audit note in `reconciliation`; only after that may a later call execute.
5. The executor enforces its own deadline: the adapter call may not outlive `envelope.timeout_seconds` (R28a adds the `asyncio` timeout; this packet only relies on `timeout + grace` for takeover).

## Negative tests (marker `integration`; child processes via `multiprocessing.get_context("spawn")`; the adapter's side effect is appending one line to a temp file so the parent can count real executions)

- `test_kill_after_side_effect_before_finalize_reconciles_to_succeeded_once` — child: `begin_execution`, append line, `os._exit(9)`. Parent (grace shortened through constructor args, not a sleep-free mock): same envelope → orphan → `unknown` → reconcile observes the line → `succeeded`. File has exactly 1 line; receipts: one `succeeded` with `reconciliation_state="reconciled"`.
- `test_kill_before_side_effect_retries_exactly_once` — child exits right after `begin_execution`. Parent: orphan → `unknown` → `not_applied` → second attempt executes. File has exactly 1 line; `attempt_count == 2`; receipts ordered `failed`, `succeeded`.
- `test_live_executor_is_not_taken_over` — row younger than `timeout + grace` → `effect_already_executing`; adapter not called.
- `test_orphan_never_returns_to_reserved` — after recovery the state history contains no `reserved`.
- `test_irreversible_not_applied_requires_operator_rearm`
- `test_reconcile_garbage_verdict_stays_unknown_and_never_executes`

## Evidence gate

Focused tests on real Postgres with real SIGKILL-equivalent exits, five consecutive green runs. This is `impl_complete` evidence. The counted live proof is CP5 (R33b).

## Exit

Tests green five times; ruff and mypy clean; spec's error strings present verbatim.

## Do not

Do not add a background sweeper thread or scheduler. Recovery is lazy, per row, on the next request for that `effect_key`. Do not shorten `grace_seconds` below 30 in production defaults.

## Forward-compat

V1.8 restore/reconcile (`18-07`) calls the same `unknown` path for every effect that was `executing` at the backup consistency point ("unknown effects preserved"). V2.0's response-loss drill reuses the two kill tests unchanged.
